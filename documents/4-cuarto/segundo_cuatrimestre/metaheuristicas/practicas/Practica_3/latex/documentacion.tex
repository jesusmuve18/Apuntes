    \section{Descripción del problema}

    El Problema de Agrupamiento con Restricciones (PAR), también conocido como \textit{Constrained Clustering}, consiste en la partición de un conjunto de $n$ datos o instancias en $k$ grupos (clústeres) disjuntos, basándose en la similitud de sus características y cumpliendo en la mayor medida posible un conjunto de restricciones impuestas sobre los pares de instancias. \\
    
    Formalmente, sea $X = \{x_1, x_2, \dots, x_n\}$ un conjunto de $n$ elementos en un espacio de dimensión $d$. El objetivo es encontrar una partición $C = \{C_1, C_2, \dots, C_k\}$ tal que se minimice la dispersión intra-clúster (medida como la distancia euclídea de cada elemento al centroide de su clúster), sujeta a un conjunto de restricciones a nivel de instancia (de tipo Must-Link y Cannot-Link). \\
    
    Hay 2 tipos de restricciones posibles sobre 2 instancias $x_i,x_j\in X$:
    \begin{itemize}
        \item \textit{Must-Link} (ML). Los elementos $x_i$ y $x_j$ deben pertenecer al mismo clúster.
        \item \textit{Cannot-Link} (CL). Los elementos $x_i$ y $x_j$ no pueden pertenecer al mismo clúster.
    \end{itemize}
    
    Dado que encontrar una solución factible que satisfaga todas las restricciones es un problema NP-completo en la mayoría de configuraciones prácticas, relajaremos el incumplimiento de estas condiciones, donde las violaciones se penalizan en la función objetivo. La función objetivo a minimizar se define como
    \begin{gather*}
        fitness(solucion) = desviacion(solucion) + \lambda \cdot infeasibility(solucion)
    \end{gather*}
    donde establecemos $\lambda = \frac{max_ {dist}(X)}{restricciones(R)}$ para asegurar que la infactibilidad y la desviación tienen la suficiente relevancia. Además, la desviación de una solución se define como 
    \begin{gather*}
        desviacion(C_s) = \frac{1}{k} \sum_{C_i\in C_s} \frac{1}{|C_i|} \sum_{\vec{x_j}\in C_i} \left\|\vec{x_j} - \frac{1}{|C_i|} \sum_{x_j\in C_i} \vec{X_j}\right\|
    \end{gather*}
    y la infactibilidad como el número de condiciciones inclumplidas de una solución.

    \section{Aplicación de los algoritmos empleados}

    Para la resolución del PAR mediante los algoritmos Aleatorio, Greedy y Búsqueda Local, es necesario establecer un marco de trabajo común que defina cómo se representan, evalúan y manipulan las soluciones.

    \subsection{Esquema de representación de soluciones}
    Una solución $S$ se representa como un vector de tamaño $n$ (número de instancias), donde el índice $i$ representa la instancia $x_i$, y el valor almacenado en $S[i]$ indica el índice del clúster al que ha sido asignada.
    \begin{gather*}
        S = [c_0, c_1, \dots, c_{n-1}] \quad \text{donde} \quad c_i \in \{0,1, \dots, k-1\}
    \end{gather*}
    Esta representación garantiza que toda instancia pertenezca a un clúster y solo uno. 

    \subsection{Esquema de representación de restricciones}
    Para representar el conjunto de restricciones $R$ se pueden usar dos estrategias principalmente, según convenga para mayor eficiencia en las evaluaciones de una solución:
    \subsubsection{Forma Matricial}
    El conjunto $R$ se representa como una matriz de dimensión $n\times n$ donde cada elemento $R_{ij}$ representará la restricción existente entre la instancia $x_i$ y la $x_j$. Podrá tomar los siguientes valores:
    \begin{itemize}
        \item $R_{ij} = 1$: Indica una restricción \textit{Must-Link}.
        \item $R_{ij} = -1$: Indica una restricción \textit{Cannot-Link}.
        \item $R_{ij} = 0$: Indica que no existe ninguna restricción entre $x_i$ y $x_j$.
    \end{itemize}
    Por la naturaleza de esta matriz será cuadrada, simétrica y los elementos de la diagonal principal no podrán valer $-1$. Es muy útil para saber si 2 elementos tienen alguna restricción entre ellos.

    \subsubsection{Forma Vectorial}
    En este caso se ha creado un nuevo tipo de dato llamado ``Restricción'' y tendrá la siguiente estructura:

\begin{lstlisting}[language=C++,mathescape=true, caption={Estructura de una restricción vectorial}, label={lst:VresStructure}]
struct Restriccion:
    i,j       // Indices de los puntos $x_i$ y $x_j$ que participan en la restricción
    tipo      // 1 para Must-Link, -1 para Cannot-Link
\end{lstlisting}
    De esta forma, el conjunto de restricciones $R$ será un vector de ``Restricciones'' según acabamos de describir. Aunque esta estructura sea peor para saber si 2 elementos tienen alguna restricción, es mucho mejor para recorrer las restricciones una por una para cálculos como la infactibilidad.

    \subsection{Criterio de validación de Soluciones}
    Dado que el problema establece que hay un número $k$ de clústeres para la solución se considerará que una solución $S$ es válida si y solo si aparecen todos los clústeres en la solución, es decir, si se verifica que 
    \begin{gather*}
        c_i\in S \ \ \ \ \forall c_i\in \{0,1,...,k-1\} 
    \end{gather*}

    \subsection{Reparación de soluciones no válidas}
    El proceso de reparación de una solución $S$ con clústeres vacíos consistirá en seleccionar un elemento $c_0\in S$ que aparezca al menos 2 veces en el vector (para no dejar dicho clúster vacío) y sustituir su valor por el índice del clúster vacío. Se repite este proceso hasta que no haya clústeres vacíos. Seguiría el siguiente esquema:

\begin{lstlisting}[language=C++,mathescape=true, caption={Pseudocódigo de la reparación de una solución}, label={lst:fixSolution}]
Función RepararSolucion(S):
    // Inicializamos el vector n_puntos con el número de puntos de cada clúster en la solucion S
    n_puntos = nPuntosClusteres(S)

    Para cada clúster c desde 0 hasta $k-1$:
        Si n_puntos[c] == 0:
            arreglado = Falso
            instancia = 1
            
            // Buscar una instancia de un clúster con más de 1 elemento
            Mientras arreglado == Falso y instancia $\leq$ n:
                cluster_actual = S[instancia]
                
                Si n_puntos[cluster_actual] > 1:
                    // Reasignar al clúster vacío
                    S[instancia] = c_vacio       
                    n_puntos[cluster_actual] = n_puntos[cluster_actual] - 1
                    n_puntos[c_vacio] = n_puntos[c_vacio] + 1
                    arreglado = Verdadero

                instancia++

    return S
\end{lstlisting}
    
    \subsection{Evaluación de una solución (función objetivo)}
    La evaluación de una solución requiere calcular los centroides de los clústeres a partir de las asignaciones actuales en $S$, calcular la desviación media de cada clúster y contabilizar las restricciones violadas consultando la matriz $R$. Esto se hará de la siguiente forma:
    
    \subsubsection{Cálculo de centroides de una solución}

\begin{lstlisting}[language=C++, mathescape=true, caption={Pseudocódigo del cálculo de los centroides de una solución}, label={lst:getcentroids}]
Funcion obtenerCentroides(S):
    n_puntos = nPuntosClusteres(S)

    // Recorro todos los vectores sumándolos a su cluster
    Para cada instancia i de X:
        cluster = S[i]
        Para cada dimension d de la instancia i:
            centroides[cluster].coordenada[d] += X[i].coordenada[d]
    

    // Divido entre el número de cada cluster para calcular la media
    Para cada cluster c desde 0 hasta $k-1$
        Para cada dimension d del centroide centroides[c]:
            centroides[c].coordenada[d] /= n_puntos[c]

    return centroides
\end{lstlisting}

    \subsubsection{Cálculo de la desviación de una solución}
    
\begin{lstlisting}[language=C++, mathescape=true, caption={Pseudocódigo del cálculo de la desviación de una solución}, label={lst:desviation}]
Función Desviacion(S):
    centroides = obtenerCentroides(S)
    n_puntos = nPuntosClusteres(S)

    // Sumamos las distancias
    Para cada instancia i de X:
        cluster = S[i]
        $distancia_{ic}$[cluster] += distancia(X[i], centroides[cluster])

    desviacion = 0

    // Sumamos la media de las distancias
    Para cada clúster c desde 0 hasta $k-1$
        Si n_puntos[c] > 0:
            desviacion += ($distancia_{ic}$[c]/n)

    return (desviacion/k)
\end{lstlisting}

    \subsubsection{Cálculo de la infactibilidad de una solución}
    
\begin{lstlisting}[language=C++, mathescape=true, caption={Pseudocódigo del cálculo de la infactibilidad de una solución}, label={lst:infeasibility}]
Función Infactibilidad(S):
    inf = 0

    Para cada restricción res en el conjunto de restricciones R
        juntos = (S[res.i] == S[res.j])

        Si res es de tipo ML y !juntos:
            inf++ // Error: Deberían estar juntos (Must-Link)
        Sino si res es de tipo CL y juntos:
            inf++ // Error: No deberían estar juntos (Cannot-Link)
    
    return inf
\end{lstlisting}

    \subsubsection{Evaluación de una solución}
    Finalmente, usando las funciones previamente descritas, y previamente fijado el valor de lambda, la función objetivo se calculará de la siguiente forma
\begin{lstlisting}[language=C++, mathescape=true, caption={Pseudocódigo del cálculo de la función objetivo}, label={lst:infeasibility}]
Evaluacion(S) {
        C = Desviacion(S)
        inf = Infactibilidad(S)

        return (C + lambda * inf)
    }
\end{lstlisting}

% ------------------------------------------------------------------
\subsection{Enfriamiento Simulado (ES)}
 
El algoritmo ES parte de una solución inicial aleatoria y permite aceptar soluciones
peores con una probabilidad decreciente controlada por la temperatura.  A continuación
se detalla su estructura completa, reflejando fielmente la implementación realizada.
 
\subsubsection*{Cálculo de la temperatura siguiente (esquema de Cauchy modificado)}
 
\begin{lstlisting}[language=C++, mathescape=true,
    caption={Pseudocódigo del esquema de enfriamiento de Cauchy modificado},
    label={lst:nextT}]
Función nextT(beta, T):
    return T / (1.0 + beta * T)
\end{lstlisting}
 
\subsubsection*{Algoritmo principal ES}
 
\begin{lstlisting}[language=C++, mathescape=true,
    caption={Pseudocódigo del Enfriamiento Simulado (ES)},
    label={lst:es}]
Función ES.optimize(problem, maxevals, solucion_inicial):
    n          = problem.getSolutionSize()
    max_vecinos = 10 * n
    max_exitos  =  1 * n
    M           = maxevals / max_vecinos    // número de enfriamientos
 
    // Inicialización
    solucion = solucion_inicial
    Si !problem.isValid(solucion): problem.fix(solucion)
 
    info    = problem.generateFactoringInfo(solucion)
    evals   = 1
    fitness_actual  = info.fitness
    mejor_solucion  = solucion
    mejor_fitness   = fitness_actual
 
    // Cálculo de temperaturas y beta
    T0   = (mu * fitness_actual) / (-ln(phi))
    Tf   = 1e-3
    Si Tf >= T0: Tf = T0 * 1e-3
    beta = (T0 - Tf) / (M * T0 * Tf)
    T    = T0
 
    // Dominio de la solución
    [k_min, k_max] = problem.getSolutionDomainRange()
 
    // Bucle principal
    Mientras evals < maxevals:
        n_exitos  = 0
        n_vecinos = 0
 
        // Construir lista de movimientos válidos (i, nuevo_cluster)
        moves = obtenerVecindario(solucion)
        
        // Barajar aleatoriamente para explorar sin repetición
        Random.shuffle(moves)
 
        // --- Bucle interno L(T) ---
        Para cada (pos, nuevo_cluster) en moves:
            Si evals   >= maxevals:        salir
            Si n_vecinos >= max_vecinos:   salir
            Si n_exitos  >= max_exitos:    salir
 
            // Evaluación incremental del vecino
            fitness_vecino = problem.fitness(solucion, info, pos, nuevo_cluster)
            evals++
            n_vecinos++
 
            delta_f = fitness_vecino - fitness_actual
 
            // Criterio de aceptación
            Si delta_f < 0:
                aceptar = Verdadero             // mejora: siempre aceptar
            Sino:
                prob    = exp(-delta_f / T)
                aceptar = (Random.uniforme(0,1) <= prob)
 
            Si aceptar:
                solucion.AplicarCambio(pos, nuevo_cluster)
                n_exitos++
 
                Si fitness_actual < mejor_fitness:
                    mejor_fitness  = fitness_actual
                    mejor_solucion = solucion
 
        // Condición de convergencia: ningún éxito en este enfriamiento
        Si n_exitos == 0: salir del bucle principal
 
        // Aplicar esquema de Cauchy
        T = nextT(beta, T)
 
    return (mejor_solucion, mejor_fitness, evals)
\end{lstlisting}

\subsection{Búsqueda Multiarranque Básica (BMB)}
 
La BMB genera \texttt{n\_arranques} soluciones iniciales aleatorias independientes,
aplica la Búsqueda Local (BL) sobre cada una de ellas y retiene la mejor solución global.
 
\begin{lstlisting}[language=C++, mathescape=true,
    caption={Pseudocódigo de la Búsqueda Multiarranque Básica (BMB)},
    label={lst:bmb}]
Función BMB.optimize(problem, maxevals):
    // Parámetros: n_arranques = 5, maxevals_bl = 20000
    mejor_solucion = vacía
    mejor_fitness  = +$\infty$
    total_evals    = 0
 
    Para t desde 0 hasta n_arranques - 1:
        Si total_evals >= maxevals: salir
 
        // Evaluaciones disponibles para esta ejecución de BL
        evals_restantes = min(maxevals_bl, maxevals - total_evals)
 
        // Ejecutar BL con solución inicial aleatoria nueva
        resultado = BusquedaLocal(problem, evals_restantes)
        total_evals += resultado.evaluaciones
 
        // Actualizar mejor global
        Si resultado.fitness < mejor_fitness:
            mejor_fitness  = resultado.fitness
            mejor_solucion = resultado.solucion
 
    return (mejor_solucion, mejor_fitness, total_evals)
\end{lstlisting}

\subsection{Búsqueda Local Reiterada (ILS-BL)}
 
El esquema ILS combina la BL con un operador de mutación que perturba la mejor
solución encontrada para escapar de óptimos locales.  La clase base \texttt{ILSBase}
contiene tanto el operador de mutación como el bucle principal; la subclase
\texttt{ILSAlgorithm} instancia el algoritmo de optimización interno con la BL.
 
\subsubsection*{Operador de mutación}
 
\begin{lstlisting}[language=C++, mathescape=true,
    caption={Pseudocódigo del operador de mutación del ILS},
    label={lst:mutate}]
Función ILSBase.mutate(solucion, k_min, k_max, problem):
    n       = solucion.size()
    n_mutar = round(p_mutacion * n)    // p_mutacion = 0.2
    Si n_mutar < 1: n_mutar = 1
 
    // Permutación aleatoria de índices; tomamos los primeros n_mutar
    indices = [0, 1, ..., n-1]
    Random.shuffle(indices)
 
    k_rango = k_max - k_min + 1
 
    Para t desde 0 hasta n_mutar - 1:
        pos = indices[t]
        cluster_actual = solucion[pos]
 
        // Elegir un cluster distinto al actual
        Repetir:
            nuevo_cluster = Random.entero(k_min, k_max)
        Hasta que nuevo_cluster != cluster_actual  O  k_rango == 1
 
        solucion[pos] = nuevo_cluster
 
    // Reparar si la mutación dejó algún cluster vacío
    Si !problem.isValid(solucion): problem.fix(solucion)
\end{lstlisting}
 
\subsubsection*{Bucle principal ILS}
 
\begin{lstlisting}[language=C++, mathescape=true,
    caption={Pseudocódigo del bucle principal de ILS},
    label={lst:ils}]
Función ILSBase.optimize(problem, maxevals):
    // Parámetros: n_arranques = 5, maxevals_algorithm = 20000, p_mutacion = 0.2
    [k_min, k_max] = problem.getSolutionDomainRange()
    total_evals = 0
 
    // Primera aplicación del algoritmo de optimización (solución aleatoria)
    evals_restantes = min(maxevals_algorithm, maxevals - total_evals)

    // Optimizamos mediante el algoritmo elegido
    resultado_inicial = optimizeAlgorithm(problem, evals_restantes)
    total_evals += resultado_inicial.evaluaciones
 
    mejor_solucion = resultado_inicial.solucion
    mejor_fitness = resultado_inicial.fitness
 
    // Bucle principal: n_arranques - 1 iteraciones adicionales
    Para t desde 1 hasta n_arranques - 1:
        Si total_evals >= maxevals: salir
 
        // Mutar la mejor solución encontrada hasta ahora
        mutada = copiar(mejor_solucion)
        mutate(mutada, k_min, k_max, problem)
 
        // Aplicar el algoritmo de optimización sobre la solución mutada
        evals_restantes = min(maxevals_algorithm, maxevals - total_evals)
        // Optimizamos mediante el algoritmo elegido
        resultado_bl = optimizeAlgorithm(problem, evals_restantes, mutada)
        total_evals += resultado_bl.evaluaciones
 
        // Criterio del mejor: actualizar solo si hay mejora
        Si resultado_bl.fitness < mejor_fitness:
            mejor_fitness = resultado_bl.fitness
            mejor_solucion = resultado_bl.solucion
 
    return (mejor_solucion, mejor_fitness, total_evals)
\end{lstlisting}
 
En \texttt{ILSAlgorithm}, \texttt{optimizeAlgorithm} delega en la BL estándar:
\begin{lstlisting}[language=C++, mathescape=true,
    caption={Pseudocódigo de ILS-BL},
    label={lst:ilses}]
Función ILSAlgorithm.optimizeAlgorithm(problem, maxevals):
    return BusquedaLocal(problem, maxevals)
 
Función ILSAlgorithm.optimizeAlgorithm(problem, maxevals, solucion_inicial):
    return BusquedaLocal(problem, maxevals, solucion_inicial)
\end{lstlisting}

\subsection{Hibridación ILS-ES}
 
El algoritmo ILS-ES reutiliza íntegramente el bucle principal de \texttt{ILSBase}
(sección anterior), sustituyendo únicamente el método de optimización interna: en lugar
de la BL se emplea el ES.  La clase \texttt{ILSESAlgorithm} sobrescribe
\texttt{optimizeAlgorithm} delegando en \texttt{ESAlgorithm.optimize}.
 
\begin{lstlisting}[language=C++, mathescape=true,
    caption={Pseudocódigo de la hibridación ILS-ES},
    label={lst:ilses}]
Función ILSESAlgorithm.optimizeAlgorithm(problem, maxevals):
    return ES.optimize(problem, maxevals)
 
Función ILSESAlgorithm.optimizeAlgorithm(problem, maxevals, solucion_inicial):
    return ES.optimize(problem, maxevals, solucion_inicial)
 
// El bucle principal es idéntico al de ILSBase (véase Código Fuente~\ref{lst:ils}),
// con n_arranques = 5 y maxevals_algorithm = maxevals / n_arranques.
// Los parámetros del ES interno son phi = 0.3 y mu = 0.2.
\end{lstlisting}
 
El esquema completo de ILS-ES resulta, por tanto, de sustituir la llamada a BL en el
pseudocódigo~\ref{lst:ils} por la llamada a ES del pseudocódigo~\ref{lst:es},
manteniendo el mismo operador de mutación (pseudocódigo~\ref{lst:mutate}) y el
mismo criterio de aceptación del mejor.

    \subsection{Análisis de resultados}
 
En esta sección se analizan en profundidad los resultados recogidos en las tablas y
boxplots de las secciones anteriores.  El análisis se organiza comparando, en primer
lugar, algoritmos con mayor similitud estructural, extrayendo finalmente conclusiones sobre el comportamiento global.
 
% ------------------------------------------------------------------
\subsubsection*{Observaciones preliminares: referencias de calidad}
 
Antes de entrar en las comparaciones algorítmicas conviene establecer el rango de
calidad de las soluciones.  \textit{Greedy} y \textit{Random} constituyen los extremos
del espectro: \textit{Greedy} genera soluciones de calidad aceptable en tiempo despreciable
($\approx 1$ evaluación), mientras que \textit{Random}, a pesar de consumir las 100\,000
evaluaciones completas, produce sistemáticamente las peores soluciones en los tres
datasets. Esto refleja que la simple generación aleatoria masiva, sin ningún mecanismo
de mejora, no compensa la ausencia de búsqueda dirigida.\\

La {Búsqueda Local (\textit{BL})} supone ya un salto cualitativo muy notable: reduce el
fitness de \textit{Greedy} en torno a un 30\% en Zoo, un 17\% en Glass y un 29\% en Bupa
(restricciones al 15\,\%), empleando además muchas menos evaluaciones que los algoritmos
complejos.  Este hecho convierte a la \textit{BL} en la referencia fundamental para evaluar el
resto de técnicas (parece que por ello se ha hecho hincapié en el guion para analizar este algoritmo en concreto).
 
% ------------------------------------------------------------------
\subsubsection*{Influencia del número de arranques: BL vs. BMB}
 
La \textit{BMB} y la \textit{BL} son los algoritmos más directamente comparables: ambos aplican la misma
Búsqueda Local, pero la \textit{BMB} la lanza desde 5 puntos de partida independientes,
repartiendo las 100\,000 evaluaciones en bloques de hasta 20\,000.
 
\begin{itemize}
    \item En {Zoo} (15\,\%), la \textit{BMB} mejora claramente a la \textit{BL}: el fitness pasa de
    1.0923 a 1.0338, una reducción del 5.4\,\%.  El comportamiento se replica al 30\,\%
    (de 1.1968 a 1.1655).  Los boxplots muestran además una caja más compacta en BMB,
    lo que indica mayor estabilidad entre ejecuciones.
 
    \item En {Glass}, la mejora existe pero es menos notable: de 0.4041 a 0.3960
    (15\%) y de 0.4682 a 0.4620 (30\%).  Los patrones de fitness de Glass, con
    numerosos óptimos locales de calidad similar, hace que explorar diferentes zonas del
    espacio de búsqueda no aporte tanto como en Zoo.
 
    \item En {Bupa}, \textit{BMB} iguala o incluso empeora ligeramente a la \textit{BL}: los
    valores son prácticamente idénticos (0.1786 vs.\ 0.1702 al 15\%).  Bupa es el
    dataset más grande ($n=345$, $k=16$), lo que implica que la \textit{BL} necesita muchas más
    evaluaciones para converger (más de 80\,000).  Al dividir las evaluaciones en 5
    bloques de 20\,000, ninguna \textit{BL} individual tiene tiempo suficiente para alcanzar el
    mismo nivel de optimización que una única \textit{BL} con presupuesto completo. Este es un
    ejemplo claro de la trampa del límite de evaluaciones dividido en algoritmos
    multiarranque.
\end{itemize}
 
\noindent En conclusión, la \textit{BMB} supera a la \textit{BL} cuando las instancias son pequeñas o
medianas (Zoo, Glass), aprovechando la diversidad de puntos de partida.  Sin embargo,
en instancias grandes donde la \textit{BL} requiere muchas evaluaciones para madurar, el
número de evaluaciones dividido penaliza a la \textit{BMB}.
 
% ------------------------------------------------------------------
\subsubsection*{Importancia de la memoria: BMB vs. ILS-BL}
 
La \textit{ILS-BL} y la \textit{BMB} son estructuralmente muy parecidas: ambas lanzan 5 aplicaciones de
la \textit{BL} con un presupuesto de 20\,000 evaluaciones cada una. La única diferencia reside
en cómo se genera el punto de partida de cada \textit{BL}: la \textit{BMB} lo genera aleatoriamente
y de forma independiente, mientras que la \textit{ILS-BL} muta la mejor solución
encontrada hasta el momento.
 
\begin{itemize}
    \item En {Zoo}, los resultados de \textit{ILS-BL} y \textit{BMB} son casi idénticos (1.0329
    vs. 1.0338 al 15\%; 1.1786 vs.\ 1.1655 al 30\%).  La pequeña ventaja de \textit{BMB}
    al 30\% podría indicar que en ese escenario la mayor diversidad de arranques
    aleatorios es ligeramente más beneficiosa que la explotación guiada por mutación.
 
    \item En {Glass}, la \textit{ILS-BL} aventaja a la \textit{BMB} de forma más clara (0.3897
    vs. 0.3960 al 15\%).  Aquí el operador de mutación, que cambia solo el 20\%
    de los genes, permite explorar vecindades prometedoras sin alejarse demasiado del
    óptimo local previo.
 
    \item En {Bupa} la ventaja de \textit{ILS-BL} sobre \textit{BMB} es visible: 0.1734 vs.\
    0.1786 al 15\,\% y 0.1986 vs.\ 0.2040 al 30\,\%.  En este dataset de mayor
    complejidad, la continuidad proporcionada por la mutación permite que la BL parta de
    soluciones ya parcialmente optimizadas, compensando el presupuesto limitado.
\end{itemize}
 
\noindent En conjunto, \textit{ILS-BL} es igual o mejor que \textit{BMB} en todos los casos considerados,
lo que confirma que reutilizar información de la mejor solución previa mediante
una perturbación calibrada es una estrategia más eficiente que reiniciar completamente.
Los boxplots respaldan esta conclusión: \textit{ILS-BL} presenta dispersiones similares o menores
que BMB en todos los datasets.
 
% ------------------------------------------------------------------
\subsubsection*{Exploración del espacio vs.\ calidad local: BL vs.\ ES}
 
La comparación entre \textit{BL} y \textit{ES} es especialmente relevante porque ambos algoritmos
son de trayectoria única: en lugar de múltiples reinicios, el \textit{ES} intenta superar los
óptimos locales aceptando temporalmente soluciones peores.
 
\begin{itemize}
    \item En {Zoo}, \textit{ES} supera notablemente a la \textit{BL}: 0.9848 vs. 1.0923 al
    15\% (mejora del 9.8\%) y 1.1620 vs. 1.1968 al 30\%.  La posibilidad de
    escapar de óptimos locales mediante el criterio de vecindario es especialmente
    ventajosa en Zoo, donde el espacio de búsqueda tiene barreras locales significativas
    entre zonas de alta calidad.
 
    \item En {Glass}, el \textit{ES} no supera a la \textit{BL}: 0.3999 vs. 0.4041 al 15\%
    (diferencia insignificante) y 0.4782 vs. 0.4682 al 30\%.  En Glass,\textit{BL} ya encuentra buenas soluciones con pocas evaluaciones; el tiempo adicional que dedica el \textit{ES} a explorar con temperatura alta
    no aporta un beneficio neto.
 
    \item En {Bupa}, el \textit{ES} produce los peores resultados entre los algoritmos
    avanzados: 0.2283 vs. 0.1702 al 15\%.  Este es el resultado más llamativo de
    toda la práctica. Una explicación plausible es que con $n=345$ y $k=16$, el
    vecindario es enormemente grande ($>5{,}000$ movimientos por iteración), y la
    temperatura inicial $T_0$ calculada a partir de $\mu \cdot \text{fitness}(S_0)$ puede
    resultar demasiado elevada, aceptando casi cualquier movimiento en las primeras
    iteraciones y perdiendo la dirección de mejora. Además, el esquema de Cauchy hace
    que el enfriamiento sea lento en instancias grandes, dejando pocas evaluaciones para
    la fase de explotación a baja temperatura.
\end{itemize}
 
\noindent Los boxplots ilustran además que el \textit{ES} presenta menor dispersión que la \textit{BL} en
Zoo (las cajas son más estrechas), mientras que en Bupa la dispersión del \textit{ES} es
comparable aunque los valores medios son peores.
 
% ------------------------------------------------------------------
\subsubsection*{Hibridación: ILS-BL vs. ILS-ES}
 
Comparar \textit{ILS-BL} con \textit{ILS-ES} permite aislar el efecto de sustituir la \textit{BL} interna por \textit{ES}.
 
\begin{itemize}
    \item En {Zoo}, \textit{ILS-ES} obtiene el mejor fitness de todos los algoritmos
    evaluados: 0.9701 al 15\% y 1.1462 al 30\%, superando a \textit{ILS-BL} (1.0329 y
    1.1786). Aquí la combinación de perturbación (mutación del 20\%) con un
    optimizador que acepta empeoramientos genera una exploración más amplia del espacio
    de búsqueda.
 
    \item En {Glass}, \textit{ILS-ES} es ligeramente peor que \textit{ILS-BL} (0.4020 vs. 0.3897
    al 15\%; 0.4799 vs. 0.4604 al 30\%). Dado que el \textit{ES} individual ya era
    comparable a la \textit{BL} en Glass, la degradación introducida por usar \textit{ES} como optimizador
    interno se amplifica al encadenarlo en el esquema \textit{ILS}.
 
    \item En {Bupa}, \textit{ILS-ES} es muy similar a \textit{ILS-BL} en términos de fitness
    medio (0.2286 vs. 0.1734 al 15\%). La desventaja heredada del \textit{ES} en esta
    instancia se propaga al esquema \textit{ILS}: incluso con el mecanismo de mutación y
    reencadenamiento, el \textit{ES} no consigue ajustar la solución tan bien como la \textit{BL} en
    un espacio de alta dimensionalidad.
\end{itemize}
 
\noindent En resumen, \textit{ILS-ES} es la mejor opción en datasets con
barreras locales pronunciadas (Zoo), pero no generaliza su ventaja a todos los datasets.
La elección del optimizador interno en \textit{ILS} es, por tanto, dependiente del problema.
 
% ------------------------------------------------------------------
\subsubsection*{Efecto del porcentaje de restricciones}
 
Al pasar del 15\% al 30\% de restricciones, el fitness de todos los algoritmos
aumenta de forma sistemática, dado que la penalización por infactibilidad se vuelve más
relevante. Sin embargo, el incremento no es uniforme entre algoritmos:
 
\begin{itemize}
    \item En {Zoo}, el \textit{ES} y el \textit{ILS-ES} muestran los aumentos más moderados (\textit{ES}:
    $+0.177$; \textit{ILS-ES}: $+0.176$), mientras que la \textit{BL} crece algo más ($+0.105$).  La
    capacidad del \textit{ES} de aceptar movimientos de empeoramiento le permite explorar zonas
    factibles que la \textit{BL} no alcanzaría al estar atrapada en un óptimo local infactible.
 
    \item En {Bupa}, el \textit{ES} y el \textit{ILS-ES} ya eran los peores al 15\% y el
    incremento hasta el 30\% es similar al del resto de algoritmos, confirmando que
    el problema principal del \textit{ES} en Bupa es estructural, no específico del nivel de
    restricciones.
\end{itemize}

\subsubsection*{Comparación con el mejor algoritmo de la Práctica 2 (AM-BEST)}
 
El mejor algoritmo de la Práctica 2 (algoritmo memético \textit{AM-BEST}) sirve de referencia
de los métodos de búsqueda con poblaciones. Los resultados muestran que:
 
\begin{itemize}
    \item En {Zoo}, todos los algoritmos de trayectoria de esta práctica (salvo
    el \textit{ES} y el \textit{ILS-ES}) obtienen fitness similares a \textit{AM-BEST} o ligeramente peores.  \textit{ES} e
    \textit{ILS-ES} son los únicos que superan consistentemente al \textit{AM-BEST}, lo que evidencia la
    potencia de la aceptación de empeoramientos en instancias con muchas barreras locales.
 
    \item En {Glass} y {Bupa}, \textit{AM-BEST} y los algoritmos de esta práctica
    se sitúan en rangos de fitness muy cercanos.  La \textit{BL}, la \textit{BMB} y el \textit{ILS-BL} igualan o
    superan ligeramente a \textit{AM-BEST} en Glass, mientras que en Bupa el \textit{AM-BEST} es decente
    pero la \textit{BL} y el \textit{ILS-BL} lo superan.
\end{itemize}

\subsubsection*{Análisis del coste computacional}
 
En términos de tiempo de ejecución, se observa que los algoritmos más complejos no
siempre son los más costosos:
 
\begin{itemize}
    \item La \textit{BL} es la más rápida entre los algoritmos de optimización (10--765\,ms),
    gracias a su parada temprana cuando no hay mejora.
    \item El \textit{ES} y el \textit{ILS-ES} consumen los tiempos más altos en Zoo y Bupa, al agotar
    sistemáticamente el presupuesto de 100\,000 evaluaciones.
    \item BMB e \textit{ILS-BL} presentan tiempos intermedios: no siempre agotan el presupuesto
    porque cada \textit{BL} individual puede converger antes del límite de 20\,000 evaluaciones.
\end{itemize}
 
\noindent La relación calidad/tiempo más favorable corresponde a la \textit{BL} en instancias
pequeñas, y a \textit{ILS-BL} o \textit{ILS-ES} cuando se dispone de mayor presupuesto y el dataset tiene
estructura compleja (Zoo).

\subsubsection*{Conclusiones generales}
 
\begin{itemize}
    \item La \textit{BL} es una base sólida pero sufre de atrapamiento en óptimos locales,
    especialmente en instancias con muchos clústeres (Bupa) y complejos (Zoo).
 
    \item La diversificación mejora la \textit{BL} en instancias medianas: tanto \textit{BMB}
    (diversificación aleatoria) como \textit{ILS-BL} (diversificación guiada) superan a la \textit{BL} en
    Zoo y Glass.  \textit{ILS-BL} tiene ventaja cuando el número de evaluaciones por ejecución es limitado.
 
    \item El \textit{ES} es muy competitivo en datasets complejos (Zoo), donde su capacidad
    de aceptar empeoramientos le permite superar tanto a la \textit{BL} como a \textit{AM-BEST}.  Sin embargo,
    en espacios de alta dimensionalidad con $k$ grande (Bupa) su rendimiento se degrada
    notablemente.
 
    \item \textit{ILS-ES} es el mejor algoritmo en Zoo y el mejor o igual en los demás
    datasets comparado con sus pares de trayectoria.  La combinación de perturbación global
    (mutación) con optimización local capaz de escalar barreras (\textit{ES}) proporciona el mayor
    poder de exploración-explotación.
 
    \item La complejidad del problema determina qué algoritmo es más adecuado:
    no existe un algoritmo sistemáticamente mejor que el resto. El tamaño de la instancia, el número de clústeres y
    la complejidad del esquema de fitness condicionan de forma determinante la elección del
    método más apropiado.
\end{itemize}
